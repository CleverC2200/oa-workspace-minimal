# 停止规则

## 阻断分级

`identity_conflict` 不因人工重启而消失。同请求的新接收时间只有通过[已提交旧轮次校验](flow-engine-contract.md)后，才表示独立的新轮次；不能手工删除历史状态、改时间或清除隔离来放行。`prior_round_submitted` 只表示旧轮次回执可信，不代表新轮次已经审核或提交。已被严格更晚的同请求轮次取代、且可证明从未进入 Writer 的已打开轮次按 `prior_round_unsubmitted` 只保留展示与投影，不再阻断整轮；旧 attempt 字节不变，新轮次仍重新取材、审核和授权。其余 `identity_conflict`（含任何写入边界证据、未知写入、多版本或时间不可信）仍不可手工清除，只能按隔离排障与恢复继续调查。

控制器只使用以下三级结果，不得因为笼统的 `degraded`、历史失败数量或单据业务判断困难停止整轮：

生产调度已获得明确的有限恢复授权时，可使用 `--recover-confirmed-no-write-once YES`。控制器在全局租约内重新完整对账，仅选择已授权流程、精确仍在待办、未命中已办、允许失败类别且有可信单据级未写入证据的首个 attempt；原证据不变，通过既有恢复入口创建新 attempt。每个单据轮次最多一次跨轮恢复，已有后续 attempt 的失败进入人工接管。未传此参数的调用继续按默认规则排除历史隔离；未知写入与身份/冻结冲突不属于该授权范围。详情见[阻断处置手册](../../../../docs/runbooks/blocking-recovery.md)。

1. **正常业务结果**：材料关系不明、证据不足、规则口径模糊以及业务 `fail/uncertain` 均形成财务意见并继续 FIFO。
2. **单据级人工隔离**：只有控制器能验证当前 attempt 仍为 `review_required / authorized`、Writer 从未开始且不存在 Writer 边界、执行回执、审核决定、签字意见或提交信封时，才允许隔离当前单据并继续。当前仅包括允许的材料采集局部失败、一次有界重试后仍无效的审核决定，以及 AI 子进程完成两次安全尝试后仍为 `codex_process_failed` 或 `codex_process_incomplete`。AI 失败还必须有绑定当前 action token、模型、推理档位和两次逐次错误码的原子失败凭据，由 FlowEngine 在完成锁内复核；随后持久化为 `codex_review_failed / not_requested`。收据已写但父控制器尚未完成隔离时，仅允许完全相同证据幂等复用；冲突收据停止。历史隔离必须重新验证 action/state、收据指纹和零 Writer 痕迹后才能从可处理待办中排除，不得自动恢复或重试。
3. **全局安全停止**：登录/会话/执行身份、流程授权、冻结状态、提交目标或写入结果不可信，进程超时或卡死，本机 critical，显式停止，隔离落盘无法验证，以及所有未明确列入单据级白名单的新错误码，均停止新领取和新 OA 写请求。失败停止留下 `stop_requested:<reason>` 标记后不得由调度路径确认或移动；只有操作人已核实该原因对应的历史未知写入不再属于实时待办（只读对账判为已办或不可见），并满足控制器与全局 Writer 空闲、实时身份与执行回执可信时，才使用受控入口 `python -m apps.oa_finance_preaudit.stop_recovery` 按精确原因清除，并保留停止证据哈希、绑定 attempt 指纹与对账快照回执。

控制器内部为回收子进程设置的 `controller_cycle_stop` 只在本轮生效；控制器、全局 Writer、请求 Writer 和全部子进程可靠回收后必须自动清除。`write_state=unknown`、不可信恢复现场和人工停止标志不得自动清除。新错误码默认进入全局安全停止，只有新增真实调度缝隙的回归测试并证明 Writer 未开始后，才能加入单据级白名单。

重复启动遇到 `production_rolling_controller_active` 时，滚动 CLI 仅在当前没有停止门、运行清单有效且为 running、活动锁所有者与清单一致、fresh process 已验证且代码仍匹配时返回 `status=skipped` 和该 `reason`，不发送或清除告警。调用方到此跳过本轮，不重新启动控制器或并行处理包装；这不是财务处理完成回执。无法验证这些条件仍保留原失败及故障提醒。

下列执行安全问题属于技术失败，停止当前执行并报告脱敏原因：

- requestId 或业务流程编号无法唯一定位，包括业务流程编号数据库精确查询返回零条或多条；
- 业务流程编号数据库查询不可用、超时或失败；
- OA 登录失败、OA 会话过期，或当前本地 RPA/CDP 会话缺失、失效、不可用；
- 当前 OA 执行身份或流程授权无法可信确认；
- 当前动作、状态、冻结文件、指纹或 action token 不一致；
- 写入授权、提交目标或提交结果不可信；
- FlowEngine 无法安全持久化唯一 attempt；
- 只读测试过程中出现任何写入、流转或 automation 变更请求。

正常取得的当前材料确实缺项、有效证据关系不明或规则口径不足时，Agent 使用业务 `⚠️` 交财务判断。自动采集或读取失败按[FlowEngine 合同](flow-engine-contract.md)停止当前单据，不能以空降级包继续提交。

登录或会话失效不能转换成业务 `⚠️`：当前 attempt 直接返回技术失败，不生成材料、审核包、决定、意见或写入请求，并停止本轮继续领取。登录恢复后也不得自动重试历史 `needs_admin`；按人工对账和显式恢复规则处理。

用户明确要求开发排障或清理历史隔离时，转到[隔离排障与恢复](../../../../docs/agents/quarantine-repair.md)继续诊断、回测和已授权的显式恢复。上述停止规则约束当前审批执行，不表示开发任务可在隔离后结束；缺陷修复和单批恢复须分别提供完成证据。

控制器终态只有在实际子进程全部退出后才能记录 `children_reaped=true`。若失败终态因瞬时回收误报遗留 `children_reaped=false`，后续运行默认继续阻断；只有操作人已通过只读状态和系统进程核实停止原因为 `controller_cycle_stop`、原控制器 PID、全局 Writer、请求 Writer 和全部子进程均已退出，且当前身份、授权、冻结、对账与干净代码门禁可信时，才能在受控滚动入口显式确认修复该交接记录。该确认不得恢复历史 `needs_admin`、技术失败或 `write_state=unknown`，也不得覆盖触发停止的首个技术错误码。

生产 `status --check-live` 还必须读取 RPA 专用浏览器当前 OA 页面的登录状态，并通过同源、只读且需要登录的菜单接口确认服务端会话仍然有效；页面或服务端结果无法确认时一律停止。该探针不刷新页面、不调用 OA heartbeat，也不作为 OA 保活。发现会话类稳定错误码后，外部定时任务调用独立飞书告警入口，向本地私有配置指定的会话发送脱敏人工登录提示；生产滚动入口直接遇到同类错误时也执行相同告警。告警入口发送前必须重新执行当前实时会话检查：只有当前检查仍返回会话类稳定错误码才发送；历史 `needs_admin`、隔离动作或旧汇总中的会话错误不得触发新提醒。重新检查成功或无法确认错误仍属于当前会话故障时不发送提醒，但不覆盖原执行的停止结果。同一错误窗口最多尝试提醒三次；仅当既有发送已确认 `sent` 时，错误码变化开启新窗口，同码达到三次且距最近确认发送满六小时允许再次提醒。旧发送回执保留，新窗口使用独立幂等身份；`started/unknown` 不因换码或时间推移自动重试，损坏或倒退时间停止发送。实时会话恢复只清除对应会话告警窗口，不把未恢复的生产故障认定为恢复；发送失败、超时或结果未知不得覆盖原始技术失败、继续领取、写 OA 或自动重试，结果未知时不得继续尝试。人工登录且下一轮网页会话检查成功后，只清除告警去重状态，不恢复历史 attempt。

材料失败告警必须同时读取 `reason` 和 `failure_detail_code`。仅当 `reason=material_collection_failed` 且细码为上述六类登录/会话稳定码时，已授权调用方使用 `session_alert --error-code material_collection_failed --failure-detail-code <会话细码> --confirm-send YES`；入口以细码执行现有实时会话复核，当前会话正常返回 `not_required`，当前仍失败则保留当前会话错误码。其他材料细码继续使用通用材料失败告警，不把登录正常视为材料问题恢复；细码参数不能用于覆盖 Writer 等非材料故障。发送授权、去重及 unknown 保护不变，未提供细码的旧调用保持原行为；生产调用方需采用本合同，发布不自动修改工作树外定时配置。

自动采集、下载或读取失败保留脱敏技术细码与计数，停止当前单据，不转换为可提交业务意见。材料包全空或旧降级包同样在提交前阻断，当前规则见[FlowEngine 合同](flow-engine-contract.md)。正常读取的原材料真实缺项仍由 Agent 说明具体业务缺口。

业务上的 `❌/⚠️` 不是技术失败。审核标准没有足够口径、有效证据之间关系不明或无法形成准确结论时，相关项目使用 `⚠️` 并继续交财务判断，不得停止整轮。完整可信材料明确显示业务支持费流程完全没有附件时，“附件完整性”使用 `❌`；OA 声明或返回附件但自动读取失败时停止当前单据，保留材料失败证据，不得伪造证据或改走旧 runner。

包装图片校对必须有可直接观察的可信页面；图片材料不可读仍属于技术失败，不生成貌似完成的文字校对意见。

汇报时只给脱敏的失败阶段和原因，不输出附件正文、凭据、Cookie、token 或原始接口响应。
