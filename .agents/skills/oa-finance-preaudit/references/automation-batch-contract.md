# 自动化批次契约

仅在任务明确要求处理待办批次时读取。单据审核仍以主 Skill、结果契约、证据阅读规则和停止规则为准。

本契约只约束定时拉起、角色生命周期、调度、隔离、运行监控、故障恢复和写入顺序。`queue_cli`、取数器和附件脚本不得生成、修正或推断财务结论；表单/附件阅读、证据关系判断以及 `✅/❌/⚠️` 意见始终由当前单据的全新原生审核 Agent 按 Skill 完成。

运行角色统一从 `apps.oa_finance_preaudit.role_cli` 进入：controller 只见刷新、快照、claim 与队首查询；reviewer 只见本 assignment 的采集、状态恢复与封存；writer 只见角色指纹和 `submit-frozen-once`；精确 `OPS_RESOLUTION` 才使用 ops 恢复入口。`queue_cli` 保留为深层实现、测试和回滚兼容面，不是普通运行角色的命令目录；角色合同中的窄入口优先于本总契约后续对内部 transition 的解释。

## 闭环控制面

- **四层角色：**自动化每小时创建一个独立可见调度任务；每个自然日只有一个当天控制台逻辑角色，且同一时刻只有一个活动控制台；每个 `requestId + received_at + attempt` 使用一个全新原生审核 Agent；用户指定的 Admin 是唯一可以修改 Skill、项目代码和 automation 的角色。小时调度任务只做当前任务登记、上一小时与跨日归档补偿、当天控制台发现/唤醒和反馈闭环；当天控制台直接协调 FIFO、租约、审核并发、事件监控和写入调用顺序，**不再为每个流程创建可见批次任务**。小时调度任务、当天控制台和审核 Agent 都不得直接修改 Skill、项目代码或 automation。
- **控制与写入分离：**当天控制台接收独立小时调度任务的 `CONTROL_START` 或 `HOURLY_WAKEUP`，直接管理当前 epoch，并兼任跨线程只读监控；审核 Agent 可以并行形成冻结材料和意见。`apps.oa_approval.frozen_writer submit` 是唯一 OA 写入入口，审核 Agent 不得调用；不同 requestId 可进入有界提交池，同一 requestId 始终单飞。
- **运行权限保持简单：**自动化在项目级预先配置可用的本地文件、生产工作树和 OA 网络权限；Skill 不新增逐命令授权、路径 ACL、Admin 授权数据库或代码级角色状态机。若平台实际拒绝所需访问，在领取新租约前报告 `permission_profile_mismatch` 给当天控制台和 Admin；不得反复弹出授权、扩大 shell 前缀或让失败租约占住队首。
- 队列状态机是唯一运行事实。生产 `status`、任务状态和相关进程是即时安全证据；automation memory 只记录脱敏的 Admin/控制台运行指针、线程登记、归档补偿、`DAILY_HANDOFF`、`OPEN_OP`、`OPS_EVENT` 与 `OPS_RESOLUTION`，不拼接队列、不保存附件正文，也不替代状态迁移。
- 每个小时控制面固定执行：cron 创建独立可见调度任务 → 登记当前精确 threadId → 补偿全部未配对的已闭合任务 → 读取当天控制台指针 → 启动或唤醒控制台 → 取得真实进度反馈 → 生成 `HOURLY_DISPATCH_RECEIPT` → 登记当前任务待归档。标题设置、归档或控制台发现失败均先持久化脱敏事件，再生成绑定当前精确 threadId 的无写入小时终态与 `ARCHIVE_PENDING`；失败任务不因缺少业务反馈永久留在侧栏。控制台 epoch 再执行刷新队列 → 调整全新审核 Agent → 领取-派发握手 → 冻结准备 → 有界提交 → 回执核验 → 故障上报或正常收尾。原生 Reviewer/Writer 自然结束；每一步只有取得下游可验证回执才进入下一步。小时任务最终回执固定为 `HOURLY_DISPATCH_RECEIPT|receipt_id=...|date=...|hour=...|generation=...|controller_thread_id=...|dispatch=...|feedback=...|write_state=...|closure=...`。
- **热路径最小门禁：**只有当前单据身份/版本不可信、附件归属或关键页面不完整、同 requestId 并行或写入结果不明确、生产登录或双源待办读取不可靠时，才阻断当前单据或整批。容量探测失败、可选观察子 Agent 不可用、时效指标缺失、归档失败、任务列表或 Goal 等非关键控制探针失败均走降级或旁路记录：不得改写财务判断，不得把安全隔离的单据转成技术阻断。四类财务报销的可选观察子 Agent 不可用时由当前审核 Agent 直接完成页面覆盖；包装默认快速路径由协调者完成关键文字覆盖自检和主审，可选独立复核不可用时仅将受影响的低置信关键区域标为 `⚠️`。时效指标缺失不得阻断审核或提交，归档失败不得阻断下一单，只记录脱敏运维事件后继续。
- 任何技术问题固定执行：保存脱敏现场 → 建立可复现检查 → 分级 → 安全闭合当前状态 → 持久化 `OPEN_OP` 并发送 `OPS_EVENT` 给 Admin → Admin 修复并聚焦验证 → 返回 `OPS_RESOLUTION` → 当天控制台使用队列命令恢复 → 恢复 automation → 恢复后进度验证。修复完成但队列未迁移、automation 未恢复或 FIFO 未继续推进，都不算闭环。

## 调度周期与完成边界

- `oa-skill` 使用项目级 hourly cron，每次触发由平台创建每小时一个独立可见调度任务，标题为 `OA财务预审小时调度 YYYY-MM-DD HH:00`。任务先以 `THREAD_REGISTER|role=hourly_launcher|thread_id=...|date=...|hour=...|generation=...` 登记自身精确身份，再归档前一小时已经闭合且回执匹配的任务；随后从 automation memory 的 `THREAD_REGISTER|role=controller|date=...|thread_id=...|generation=...` 读取当天控制台。只要顶层 `thread.id` 与登记的精确 `thread_id` 完全一致，就通过 `send_message_to_thread` 启动或唤醒。`idle` 和 `notLoaded` 都是有效状态，不得据此记录 `controller_discovery_unavailable`。
- 当天无有效控制台指针时，当前小时调度任务才允许创建一个 `gpt-5.6-terra`、`reasoning_effort=high` 的当天控制台，设置精确标题 `OA财务预审控制台 YYYY-MM-DD`，并在继续前持久化 `THREAD_REGISTER|role=controller|date=...|thread_id=...|generation=...`。不得继续复用前一日控制台，不得把 Admin 当成日常调度任务，也不得基于标题相似或旧队列创建第二控制台。
- **控制台创建回执：**调用 `create_thread` 后必须保留并输出 `create_thread` 的完整顶层返回对象，从顶层读取 `threadId` 或 `clientThreadId`；不得投影 `result.structuredContent ?? result.content`，该投影会丢失任务身份。取得真实 `threadId` 后调用 `set_thread_title` 设置精确标题 `OA财务预审控制台 YYYY-MM-DD`，再用 `read_thread` 核对任务身份。只有取得可供 `read_thread` 使用的真实 `threadId` 并完成 `DAILY_HANDOFF_ACK`，才能写入权威 `THREAD_REGISTER`；仅有 `clientThreadId` 时等待同一创建请求转为 ready，不再次创建。返回对象缺少两种 ID 时记录 `successor_create_unconfirmed`，不得更新控制台指针、归档旧控制台或启动 FIFO，并只允许一次有界恢复探针确认是否已经存在该日唯一控制台。
- **同日控制台顺序换班：**若活动审核数低于计划值，连续两个不同容量快照仍返回 `agent_thread_limit_reached`，且 roster 明确存在已完成 Agent 累积或无法释放的 `pending_init`，记录 `controller_roster_exhausted`。旧控制台停止新增 claim，先让已有审核和唯一 writer 自然闭合并生成 `DAILY_CONTROLLER_ROLLOVER|date=...|old_thread_id=...|controller_generation=...|queue_generation=...|queue_counts=...|open_ops=...|contract_sha256=...|result_contract_sha256=...`；当前小时调度任务据此创建同日后继控制台。后继只读取当前仓库、持久化 FIFO 和脱敏交接，返回 `DAILY_CONTROLLER_ROLLOVER_ACK` 后，先更新精确控制台指针，再允许旧控制台进入归档补偿。ACK 前新旧控制台不得同时 claim、不得同时运行 writer；旧控制台不得把未派发租约交给后继。该换班只刷新控制面与原生 Agent roster，不重新采集、不改变 FIFO、不复用审核对话，也不等待下一小时。
- **阻断 Goal 的同日换班：**`get_goal.status=blocked` 不是 unfinished Goal，同一控制台也不能创建替代 Goal。队列仍有 `actionable` 时不得在 blocked Goal 下继续 claim、派发或启动新的 writer，也不得发送普通 final。旧控制台发出 `CONTROLLER_ROLLOVER_REQUIRED|failure_code=controller_goal_blocked` 后停止新增动作，只让已经活动的 reviewer/writer 自然闭合并返回 `DAILY_CONTROLLER_ROLLOVER_READY`；当前小时调度任务立即按上一条创建同日后继。后继的身份预检回合只返回 `DAILY_CONTROLLER_ROLLOVER_ACK`，ACK 前不得创建 Goal、claim 或写 OA；精确指针更新后由小时调度任务发送 `CONTROL_START`，后继第一步创建 fresh unfinished Goal 并在同一回合直接排空，禁止先发 final。旧控制台随后进入归档补偿。该恢复不等待下一小时调度，不重新采集、不改变 FIFO，也不增加 writer。
- 精确指针缺失时，或 `read_thread` 未返回包含匹配 `thread.id` 的权威对象时，只执行一次 `list_threads(limit=50)` 恢复探针并按精确 `thread_id` 匹配；匹配项的 `hostId` 可用于再次读取同一任务。匹配成功后立即发送 `CONTROL_START` 或 `HOURLY_WAKEUP`，不得按标题或新旧顺序替换指针。`list_threads` 的成功空结果不得覆盖仍有效的精确指针，不受日期或最近 50 条窗口限制。两个读取接口都超时但同日精确指针已有真实运行回执时，直接向该指针发送一次 `HOURLY_WAKEUP`，以发送返回的匹配 threadId 作为交付证明。不得对控制台发现调用 `wait_threads`，也不得用固定 55/60 秒等待代替任务读取；发送后可以用 `wait_threads` 有界等待同一 receipt_id 的真实反馈。只有这些精确恢复路径都失败、超时或返回身份不一致时才记录 `controller_discovery_unavailable`；先持久化 `OPEN_OP|event_id=...|stage=controller_discovery|failure_code=controller_discovery_unavailable|thread_id=...`，再生成无写入 `HOURLY_DISPATCH_RECEIPT` 和 `ARCHIVE_PENDING`，不得报告“队列为空”、不得创建第二控制台或写入器。
- 当天控制台收到独立小时调度任务的消息后先确认 `oa-skill=ACTIVE`、原 `oa=PAUSED`，再在同一控制台内建立或合并 fresh epoch。当天控制台每小时完整拉取一次 `role_cli controller list-production-pending` 生产待办身份源和当前项目 `python3 -m apps.oa_finance_preaudit.cli list-pending`，按 requestId 取可提交交集并刷新持久化 FIFO；旧 `actionable=0` 不能作为跳过刷新或唤醒当天控制台的依据。每次小时触发都必须先刷新实时候选交集，并向当前小时调度任务回传同一 receipt_id 的真实 `PROGRESS`、`SUBMIT`、`BLOCK` 或 `EPOCH_RECEIPT`，同时报告 `last_refreshed_intersection`、`actionable`、`blocked`、`candidate_state` 和刷新时间/年龄。只有本次两个实时来源均成功、刷新时间属于当前 epoch、`candidate_state=empty` 且队列无活动审核/写入时，才可报告“队列为空”；后续 reviewer/writer 回执不得把持久快照称为实时交集。`candidate_state=all_candidates_blocked` 必须保留运维闭环，禁止表述为交集为空或待办已清空。低待办时不启动十分钟心跳、空审核 Agent 或常驻监控。
- **预检探针隔离：**线程列表、Goal、队列状态和生产状态可并行读取，但各自结果独立记录；不得调用系统 `timeout` 命令包装 Codex 工具。任一控制面探针未知时，已成功的队列和生产状态探针不得重跑；只单独重试未知的控制面探针一次。仍未知则按未知安全收尾、保留 FIFO，等待下一小时触发；不得据此推断空队列、重领或写 OA。
- 定位当天控制台失败不影响本轮归档补偿；归档补偿独立于控制台发现。下一小时调度任务重新验证精确指针；一旦当天控制台可用，先交付“刷新并合并 FIFO”再判断是否有候选。
- 当前清单处理未结束而下一小时到达时，新小时调度任务只向同一个当天控制台发送“刷新并合并清单”；当天控制台合并到当前 epoch，不新建第二控制台或第二调度层。`requestId + received_at` 未变化的租约和已冻结结果保留；普通审核租约遇版本变化时旧租约失效。处于 `submitting` 的单据不可被刷新删除、改版或转为外部阻断；发生候选消失、received_at 变化或阻断状态变化时刷新必须失败关闭，保留原 submission_token 并先核对 OA 台账。
- **常规发布延后：**Admin 在活动 epoch 中完成不改变财务口径或 OA 安全边界的修复时，只发送 `PENDING_SKILL_RELEASE|generation=...|reason=...|verification=...`；当天控制台记录并回 `PENDING_SKILL_RELEASE_ACK`。当前活动 epoch 已派发的审核和提交任务继续按已加载指纹自然闭合，但确认后停止新增 claim，避免新审核 Agent 在已变更的本地文件上误判旧 assignment 指纹。当前 epoch 无活动审核和提交任务且已生成回执后，立即创建后继 fresh epoch 读取文件、固定新指纹并发布 `SKILL_RELEASE`，不等待下一小时。涉及即时安全边界的例外必须明确标为 `EMERGENCY_SKILL_RELEASE`，才按既有代际切换门禁停止新 claim 并自然闭合；不得把普通运行修复伪装为紧急发布。
- **连续排空模式：**实时可执行交集达到 20 条时，控制台在同一个 unfinished Goal 内持续排空，不等待下一小时；**积压未清空时不得因固定时长停止新增 claim**。每 30 分钟或每闭合 10 个 attempt（先到者）建立滚动检查点，再次完整拉取两个实时来源、刷新并合并清单；若仍有候选，立即继续补满审核槽和有界提交池，无需创建人为后继 epoch。新小时调度任务只把新候选合并进当前滚动 Goal。指纹代际变化时才停止新 claim，让旧 assignment 自然闭合后载入新代际继续；不能复用旧代际 assignment、租约或冻结材料。任何实时来源失败、写入状态不明或旧代际未闭合时不得启动新代际写入。
- 每个小时快照建立“本轮已尝试 requestId 集合”。同一版本无论提交、跳过或单据级阻断，本轮只尝试一次。
- 一条完成后由当天控制台为一个全新审核 Agent 领取清单中的下一条；审核 Agent 不得自行 claim，也不得在完成一单后领取第二单。当前清单没有 `queued`、`leased`、`prepared` 或 `submitting` 项时，本 epoch 结束并等待下一小时刷新，不额外空转拉取。
- 当天控制台发送审核任务后不得结束当前 epoch；普通财务 Reviewer 和 Writer 使用 `spawn_agent(fork_turns="none")` 创建为控制台原生子 Agent，并使用 `wait_agent` 做不超过 60 秒的有界等待；不得用 `create_thread` 创建这两类角色。包装准确性协调者按用户要求使用独立可见任务，因此只对包装任务使用 `wait_threads`，其内部覆盖观察者仍为原生子 Agent。任一审核 Agent 完成或需要关注时，立即读取其闭合回执、提交当前全部可执行 prepared 单据，并继续补充审核池。只有当前清单达到上一条的闭合条件或触发整批致命失败时才结束 epoch。
- 每个自然日控制台只维护一个滚动调度 Goal：先调用 `get_goal`；没有 unfinished Goal 时才调用 `create_goal` 且不设置 token budget，已有同目标 Goal 时直接续接。目标是“持续推进实时 FIFO，直到 `actionable=0` 且没有活动审核/写入，或触发整批致命失败/用户暂停”。后续自动续回合沿用同一 Goal 和持久队列；滚动检查点只生成阶段回执和刷新清单，不完成 Goal。为防模型空转，所有等待必须事件驱动且单次不超过 60 秒；发现 backlog 存在但无活动审核/写入时必须补槽或报告容量故障，不能无界自循环。
- **结束门禁：**每次提交或审核 Agent 回执后重新读取 `role_cli controller status` 和 `get_goal`。仅当实时双源刷新成功、`actionable=0` 且没有活动审核/写入，或触发整批致命失败/用户暂停时，才调用 `update_goal(status=complete)` 并发送 final；否则必须继续提交 prepared 队首、补充审核池或有界等待活动任务。`actionable=0` 可以结束调度 Goal，但不等同于运维闭环。普通 Codex 回合提前结束时由未完成 Goal 自动续回合；滚动阶段回执、小时边界和“下一队首已 prepared”都不是 Goal 完成条件。
- 单据级失败不得结束整批；只有发生本契约定义的整批致命失败才停止全部任务。

## 持久化 FIFO 清单

- 候选只来自生产待办身份源与本项目 `list-pending` 的完整交集。任一来源不完整或生产状态不可靠时不得刷新已有清单。
- 按 `submitted_at 从早到晚` 排序；相同提交时间依次按 `received_at`、`requestId 升序`稳定排序。缺失提交时间的候选优先，避免未知老单持续沉底。
- 清单状态由 `apps.oa_finance_preaudit.queue_cli` 原子更新，不由任务在对话文本或 memory 中自行拼接。状态只保存 requestId、流程类型、时间、准备尝试号、租约、材料/意见封套指纹、结果码和脱敏写入回执，不保存附件正文、人员、公司或审批意见。
- 各单据按自身状态推进。一个 requestId 仍在取证、阻断或等待时，不得阻止其他 requestId 完成冻结校验和提交；跨单据不建立写入依赖。
- 跨轮阻断索引仍按 `requestId + received_at + failure_code + last_attempt_at + reviewer release manifest 的 SHA-256` 去重。该 manifest 同时覆盖共享结果接口与五个流程规则包，任一规则变更都不会沿用旧阻断；确定性格式阻断在版本和 reviewer release 均未变化时不得重新分配。材料类阻断采用 24 小时冷却，`received_at 变化`后立即允许新版本重试。

## 单据 Agent 与附件硬隔离

- 每个单据必须创建全新原生审核子 Agent，并使用 `fork_turns="none"`，默认模型为 `gpt-5.6-terra`、`reasoning_effort=high`。同一审核对话不得处理两个 requestId；审核 Agent 完成、阻断或异常退出后不得领取下一单。只有主 Skill 定义的高影响疑难条件才可为同一冻结材料增加一次 Sol high 隔离复核。
- 控制台通过 `role_cli controller release-manifest` 和 `role_cli reviewer release-manifest` 计算角色级 release manifest。每次 `role_cli controller claim` 必须传入 canonical reviewer manifest 的 `--reviewer-release-sha256`，状态机把它冻结到完整 assignment JSON；缺少该字段时角色入口在创建租约前拒绝。审核 Agent 只接收 `reviewer` 角色指纹与 claim 返回的完整 assignment JSON；写入器只核对 `writer` 角色指纹，dispatcher/controller 文档变更不得使已派发审核 assignment 失效。审核 Agent 使用 `fork_turns="none"`，重新读取 reviewer 合同指定的本地文件并核对本角色指纹，再处理这一个 assignment。最终 `ITEM_RESULT` 回传 `loaded_generation=...` 与 reviewer 指纹。控制台在接收回执、生成 `submission_receipt` 及 `EPOCH_RECEIPT` 前读取 `latest_generation=...`。处理中才发现代际变化时，当前 assignment 继续按已加载 reviewer 指纹自然闭合，不得重取证；只增加 `generation_transition=natural_close_old`，明确表示“自然闭合旧代际”。每次 claim 前若 reviewer 指纹或 latest_generation 已变，停止新 claim，等待已派发审核和提交任务自然闭合，再载入新 release 继续。不得把新指纹与旧 assignment 混用。取消旧常驻 worker 的 `CONTROL/CONTROL_ACK` 往返，不发送缺少 assignment JSON 的空任务。
- 每个审核 Agent 只能持有一个有效租约；租约由 `requestId + received_at + worker_id + lease_token` 唯一确定。同一 requestId 不能同时租给两个任务，任务也不能自行扫描或改领其他单据。
- 将 `role_cli controller claim` 的完整 stdout JSON 作为不可变 assignment JSON 原样转发给审核 Agent，不得从队列摘要手工重建、重写、删减或从其他位置补齐字段。创建 Agent 前必须对同一原始 JSON 机器校验 request_id、flow_key、received_at、worker_id、lease_token、isolation_key、request_root、attachment_root、prepared_root、material_file、remark_file 和 remark_envelope_file 均为非空；任一字段缺失时不创建 Agent，并使用原租约按 `assignment_payload_incomplete` 安全闭合。控制台可把 stdout 保存到 epoch 目录，但归档副本只用于审计记录；必须把 payload 内嵌的绝对 `assignment_file` 单独明确交给 reviewer 作为唯一 canonical 命令路径，所有 reviewer 命令不得传入 epoch 归档副本。claim 在发出租约前原子预建独占 attempt 根、`attachments/` 和 `prepared/`，返回的全部隔离路径均为绝对路径；审核 Agent 开始前逐项核对该包和隔离路径，根及两个子目录必须存在且为空，任一字段或目录不匹配时保持租约并报告当天控制台，不启动采集。
- **领取-派发握手：**每次 claim 前确认 epoch 尚允许领取并预留一个可用子 Agent 槽；每次只允许一个未派发租约，claim 成功后立即用完整 assignment JSON 创建全新审核 Agent，并取得任务系统的创建成功回执，再领取下一条或执行其他队列动作。未取得回执、派发前到达 epoch 边界，或回执后 Agent 没有进入活动状态时，不得把 `leased` 等同于任务正在运行；先确认对应 Agent 与相关进程均已结束，再凭该租约原 worker_id、lease_token、received_at 和机器可读死亡证明执行一次 `role_cli ops recover-stale`。若创建返回 `agent_thread_limit_reached`，只恢复这一条租约；队列的 `pool_max_workers` 或 `active_workers=0` 不等于平台实际可用槽位。恢复完成前停止新增 claim，CAS 不匹配则保持现场并报告，**不得领取第二条**。记录本次平台容量快照后保持该项 `queued`，不结束仍有 `actionable` 的 epoch：只对容量变化或已观察到审核任务自然结束后的新快照再尝试一次创建，**同一容量快照不得重复探测**。创建成功即恢复 FIFO；到达 epoch 边界仍无容量才安全收尾并上报容量受限。该恢复为**容量变化后继续**，**不等待下一小时**，且不得重领、重采集或放宽单据隔离。
- 创建前必须逐字段核对首条消息中的 assignment JSON 与本次 claim 返回一致；只有提示语而没有 JSON 时不得创建。Agent 返回 `assignment_missing` 且已经完成、没有启动采集时，恢复证明必须明确包含 `worker_inactive=true` 与 `related_process_inactive=true`；使用原租约执行一次 `role_cli ops recover-stale` 后重新 claim，并只把新 attempt 的完整 assignment JSON 交给另一个全新 Agent。
- 每次审核使用独立根目录 `requests/{requestId}/{isolation_key}/attempt-{preparation_epoch}/`，其下分别存放 `attachments/`、`prepared/`、材料 JSON、审批意见文本、`remark-envelope.json` 和提交前即时生成的 `current-proof.json`。租约恢复后必须增加 preparation_epoch；禁止复用上一次尝试目录。
- **Reviewer canonical 路径：**审核 Agent 只从项目根调用 `role_cli reviewer collect-assignment --assignment-file ASSIGNMENT`，由该命令读取并固定 requestId、attachment_root、prepared_root、material_file、单资源下载时限和脱敏失败回执；不得自行 `cd request_root`、拼接 `collect-case`、手工生成封套或调用底层 transition。Codex 完成观察与财务判断后只写 assignment 指定的 `remark_file`，再调用 `role_cli reviewer seal-review --assignment-file ASSIGNMENT ...`，由该命令生成身份封套、结果包和计时侧写并原子闭合。
- **会话闭合门禁：**以前台方式运行 `role_cli reviewer collect-assignment`，不得将 stdout 或 stderr 重定向到 `/dev/null`。若外层 `functions.exec` 返回 `Script running with cell ID ...`，必须使用同一个 `functions.wait(cell_id=...)` 继续等待，直到包装层明确完成；不得把外层 yield 当成采集失败、任务结束或无输出。随后读取内层 `exec_command` 的完整返回对象；`session_id` 非空等同于内层仍在运行，即使 `output` 为空，也必须持续对该 session 调用 `write_stdin`，直至工具明确返回 `exit_code`。原采集 PID 或 session 仍活动时不得读取材料、封存失败或启动第二个采集进程。退出码非零时只读取 assignment 绑定的脱敏失败回执并转发合法 `failure.code`；无法取得合法 code 时才使用 `material_collection_failed`。同一 attempt 禁止为补错误码重跑。
- **失败码回归矩阵：**每次调整采集失败路径至少覆盖：输出文件缺失时失败不得生成可被误认的材料；非零退出但有合法脱敏 failure.code 时必须原样保留 code；`travel_attachment_resources_incomplete` 额外只输出 `declared_attachment_count、discovered_resource_count、form_resource_count、travel_resource_count、trusted_source_sighting_count` 五个整数计数，便于区分总数不一致、唯一资源数、表单资源与商旅资源；无合法 code 时必须回退 `material_collection_failed` 且不泄露失败文本；同一 attempt 禁止为补错误码重跑。前三类以 CLI 公共 stdout 与 `--output` 文件边界验证，最后一类同时验证单次 CLI 调用只发起一次 collection 和上述会话门禁。
- **商旅资源去重与完整性：**表单资源和商旅接口资源先分别完成当前 requestId 的归属校验；两处可信来源记录数之和形成 `trusted_source_sighting_count`，用于与表单“附件数量”核对。可信来源记录数少于声明数时以 `travel_attachment_resources_incomplete` 阻断；达到声明数后，再按稳定附件 ID 合并去重并下载全部唯一资源。同一稳定附件 ID 在表单与商旅接口各出现一次是同一文件的两个可信发现记录，不得因去重后的唯一文件数小于“附件数量”误判缺失。不同下载 URL（例如签名或跳转参数变化）仍只下载一项；不得按文件名推断去重，也不得遗漏任何合并后的唯一资源。
- 任一材料 requestId、租约令牌、版本隔离键、路径归属、资源绑定或材料指纹不一致，立即以 `resource_ownership_untrusted` 或相应安全码阻断当前单据；不得复制、移动或改名后继续，也不得把另一流程的附件或意见作为证据。
- 审核 Agent 返回冻结意见时只引用本租约的材料和意见文件。当天控制台在提交前再次核对 requestId、isolation_key、material_fingerprint 三元组；不一致时禁止写 OA。

## 弹性审核池与事件驱动监控

- **三类准备通道：**普通财务报销固定拆成 `travel` 差旅保留通道和 `finance_nontravel` 非差旅财务保留通道；后者只处理业务招待费、业务支持费和小额市场费。两类均有待办时各至少保留一个单据审核槽，非差旅财务保留通道不得被差旅积压占用。`packaging` 是独立的包装准确性通道，不归入非差旅财务通道。流程类型最终只认 `collect-case.workflow_key`。
- **普通报销弹性池：**按差旅与非差旅财务的 `queued + leased` 合计积压、prepared 缓冲和任务系统实际可用槽位调整：0 条不创建普通审核 Agent，1 条使用 1 个，2–19 条保持 2 个；达到 20 条且缓冲不足时，第 3 槽才具备补位资格。prepared 缓冲充足时保持 2 个普通槽，优先让有界提交池消化。两类都有积压时各保留一个槽；额外槽优先给等待最久且缓冲不足的通道。一个 Agent 闭合一单后退出；需要继续时创建另一个全新原生子 Agent，而不是复用原对话或创建可见任务。小时调度任务只等待控制台反馈，不计入普通 reviewer 配额，禁止无上限创建任务。
- **包装关键文字优先：**每个包装单据使用一个独立包装审核对话，只处理一个 `requestId + received_at + attempt`。默认快速路径由协调者直接完成关键文字覆盖自检和主审，不启动 A/B/C；低置信、高影响数字或专名、Excel 差异或内部冲突才增加一次独立复核。用户明确要求全面逐字校对，或一次复核后关键冲突仍无法解释时，才对受影响区域升级为三路盲审。包装协调位和实际触发的视觉子 Agent 不计入普通报销审核槽位上限；平台物理槽位不足时只等待必需复核，不扩大复核范围。
- **调度与写入边界：**准备阶段允许 `travel`、`finance_nontravel`、`packaging` 各自领取 queued 单据并提前 prepared；不同 requestId 可由有界提交池并发，同一 requestId 单飞。普通池最多 3 个单据审核 Agent；包装准确性协调位独立计算，因此有包装待办时总单据协调位目标可为 4，实际运行只认平台可用容量。
- **积压容量优先级：**实时可执行普通财务积压达到 20 条且 prepared 缓冲不足时，先建立差旅和非差旅财务两个保留槽，再把剩余普通槽给等待最久且缓冲不足的通道。包装待办不等待普通积压降至阈值，立即尝试建立独立关键文字协调位；只有命中风险条件的独立复核才是对应关键区域的闭合要求，不与普通审核槽竞争配置配额。平台拒绝任务创建时记录当次 `agent_thread_limit_reached` 和完整容量快照，并精确恢复未派发租约；任一审核或观察 Agent 状态变化后重新计算三类通道，不得跨快照沿用单槽结论。
- **活动槽锚点：**审核池只以任务系统当前实际处于 running 的 `role=reviewer` 原生 Agent 数量为活动审核槽；completed、idle、创建失败、已经回收租约的任务，以及未创建成功的 leased 均不得计入活动审核槽。积压达到 20 条、`boost_eligible=true` 且平台实际允许时才持续补池到 3 个运行中审核 Agent；连续 prepared 前缀达到 2 条后不再补第 3 槽。不因控制台、dispatcher、writer 等非 reviewer 角色减少审核目标；它们只参与平台真实剩余容量判断。一次 `agent_thread_limit_reached` 只终止当前一次创建并恢复对应未派发租约，不得冻结本 epoch 的后续补池，也不得把失败探测记成运行中审核。任一 Agent 状态变化后重新读取活动 roster，按新的容量快照补池；同一快照不重复探测。
- 普通池新增容量在两个保留槽之后按等待时长、prepared 缓冲和通道积压分配；包装准确性通道独立计算。没有持续、可测量的部门积压时不按部门预建常驻任务，部门字段也不得成为业务证据。
- 两个及以上审核 Agent 活动时，由当天控制台通过原生 Agent 状态、`wait_agent` 和 `EPOCH_PROGRESS` 兼任跨线程只读监控；独立包装任务单独使用 `wait_threads`。采用事件驱动监控和不超过 60 秒的有界等待，不启动十分钟模型心跳或独立常驻监控任务。
- 审核 Agent 发现异常时，必须向当天控制台返回一行 `OPS_EVENT|severity=ITEM或BATCH|request_id=...|worker_id=...|stage=...|failure_code=...|lease_age=...|write_state=...`；未知值写 `-`。单据级事件必须包含 request_id、worker_id 和 received_at，不得在转发时删除字段；上游事件缺字段时，当天控制台必须发送前从当前队列项补齐，无法唯一补齐时报告 `ops_event_identity_missing`，不得发送身份不完整的 `ADMIN_EVENT`。当天控制台完成安全状态闭合并先持久化 `OPEN_OP` 后，使用 `send_message_to_thread` 发给 Admin。发送成功只是事件回执，不改变队列状态。
- 当天控制台发现租约疑似超时只报告。确认原 Agent 和相关进程均已结束后，由当天控制台凭原 worker_id、lease_token、received_at 和机器可读死亡证明执行一次 `role_cli ops recover-stale`；状态机使用 CAS 复核并令下一次 claim 进入新的 attempt 目录。任一证明或 CAS 不匹配时保持原租约。
- 所有审核 Agent 共享下载通道：HTTP 直连受全局容量限制，共享浏览器下载目录全局单飞，商旅浏览器按全局容量限制。等待协调槽不是附件缺失，不得绕过槽位另开下载。
- 原生观察子 Agent 只能由当前单据审核 Agent 创建，并只能在当前 requestId 的材料根目录内工作；返回必须带 resource_id、page 和当前 requestId。汇总者在覆盖门禁闭合后才生成该单意见；观察子 Agent 不得接触其他单据。
- **单据时效：**审核 Agent 在领取 assignment 后使用单调时钟分别测量单次采集、视觉观察和最终判断，阻断或成功都必须闭合脱敏阶段事件。事件按 `collect、review、coordination、wait、submit、postcheck` 记录 wall time、active time、queue wait、结果和模型；身份只保存 `requestId + received_at + attempt` 的 SHA-256。Token 只接收平台返回的精确 input/output/total usage，缺失固定记为 `unknown`，禁止估算。`item_key + event_id` 相同的重放不得重复计数，冲突值必须拒绝。指标按审核、沟通协调、等待和提交聚合；指标缺失不得阻断审核、提交或状态闭合。记录不得包含人员、公司、金额、附件名、附件正文或意见正文。
- 兼容批次回执仍可投影 `ITEM_TIMING|collection_seconds=...|observation_seconds=...|judgment_seconds=...|preparation_total_seconds=...|prepared_wait_seconds=...|writer_total_seconds=...|attempt_end_to_end_seconds=...`；这些字段只能从阶段事件或队列时间戳确定性生成，不另建第二份计时事实。

## 按请求隔离的提交池

- 窄 `frozen_writer submit` 是唯一 OA 写入入口；调度入口只负责把已经冻结的单据放入有界提交池并核验逐单回执，不承担附件阅读或财务判断。审核 Agent 不得写 OA。
- 不同 requestId 可以并发；同一 requestId 使用 requestId 级锁、一次性 token 和持久终态回执单飞。提交池上限必须同时受配置和平台实际槽位约束，不得无界创建。
- 单据级格式、租约或准备门禁故障在取得 `write_state=confirmed_no_write` 后按该项状态机安全闭合；不得阻止其他 requestId 的审核或提交。只有共享认证失效、跨单据材料串线或写入结果冲突才暂停整个提交池。
- **实时双源固定：**控制台为每次刷新或 Writer 启动分配全新的绝对目录 `runtime/finance_preaudit_queue/live-inputs/RECEIPT_ID/REQUEST_OR_REFRESH_ID/`，只调用 `role_cli controller capture-live-inputs --snapshot-dir ... --production-root ... --project-root ...`。该深 module 内部依次调用生产 `role_cli controller list-production-pending --output` 与项目 `apps.oa_finance_preaudit.cli list-pending --output`，只接受 `preaudit_production_identities_written` 与 `preaudit_case_index_written` 两种回执；生产身份源只保留 requestId、received_at、workflow identity、support status 和队列所需的兼容字段，不读取附件、不生成意见。核验完整对象/schema、绝对路径、计数与 SHA-256 后才原子发布 `live-inputs.json`。目录已存在即拒绝复用；任一来源失败时 manifest 不得存在。控制台不得手工重定向、拼接或转发两个 source 路径，也不得把 stdout、工具 output、旧 epoch 文件、`last_json` 占位路径、半成品目录或临时会话结果当成输入。
- 写入前为每个 prepared request 新建一次实时双源 manifest。生产 source 只按 `.items[].requestId` 且 `can_submit=true` 精确投影，项目 source 只按 `.cases[].request_id` 精确投影；两个 source 必须各自唯一命中一条。每个 request 独立生成 current proof：先写临时 JSON，回读成功后原子替换 final；上游失败、空输出、非法 JSON 或身份不一致时 current proof 必须不存在。禁止根据终端展示、截断片段或肉眼搜索推断身份。
- `submit-frozen-once` 在发出 token 前发现该 request 版本、待办身份或冻结指纹变化时，只保持该项 prepared 或转入相应安全状态；不影响池内其他 requestId。
- 冻结材料、意见和封套在 `seal-review` 与 `begin-submit` 阶段完成内容格式及指纹校验；窄 Writer 再机械核对四个文件位于同一 attempt，并复核 requestId、received_at、isolation_key、submission token 与 material、remark、envelope、current proof 四份 SHA-256。Writer 不读取附件正文，也不重新执行审核判断。
- **写入交接门禁：**只允许调用 `role_cli writer submit-frozen-once`。该接口在同一个前台进程内依次完成 current proof、`begin-submit`、requestId 级锁、窄冻结提交、`submission_receipt` 校验与 `mark-submitted`；控制台和 writer 不得手工拼接这些步骤。若 token 已发出但进程启动或回执解析失败，该 request 进入 unknown 对账，禁止直接重跑；其他 requestId 继续。
- canonical 单入口内部必须调用主工作树 `python3 -m apps.oa_approval.frozen_writer submit`，并完整传入 `--request-id`、`--received-at`、`--isolation-key`、`--submission-token`、`--material-file`、`--remark-file`、`--remark-envelope-file`、`--current-proof-file` 及四份 SHA-256；`--confirm-write YES` 不得省略。禁止回退到取数、流程识别、附件 AI 或规则决策路径，也禁止绕过 requestId 级锁直接提交。
- Writer 进程 `ok=true` 不能替代逐条 `submit_ok=true`、`done_hit=true`、`postcheck_done_hit=true`。canonical 单入口必须验证 request_id、submission_token、run_id、write=true 和三项布尔值后原子保存 receipt 并调用 `mark-submitted`，才能处理下一条。代际不同的阶段回执另带 `generation_transition=natural_close_old`，不得修改冻结意见。
- **写后只读确认：**窄 Writer 只在提交接口成功、已办索引命中当前 requestId、当前待办索引不再包含该 requestId 三项同时成立时返回完整成功回执。三项任一缺失或读取失败时均不得 `mark-submitted`、重试或补写。
- **单次 Writer 回执：**每个 submission token 只能对应一个有效 OA 写入和一个终态回执。相同 requestId 的并发调用等待同一锁并重放已持久回执；若同一 token 出现冲突终态，或实时 OA 状态与绑定回执互相矛盾，该 request 进入 `write_state_disputed`。
- **写入争议对账：**当前 OA 待办/已办状态与绑定 `submission_receipt` 矛盾时，该项标记 `write_state_disputed` 并保持 `blocked_external`；不得 claim、写入、`mark-submitted` 或 `requeue`。历史写入只能以精确的 `request_id + submission_token + run_id` 回执与权威 OA 当前状态复核；按 requestId 查询最近 N 条记录只可说明近期活动，**不得据此声明历史写入为 0**。两者一致后，Admin 才能给出下一步恢复或人工处理决议。
- **历史实际写入的外部闭合：**历史 `submitting` 项已确认 `write=true、submit_ok=true`，但缺少完整后置回执时，不适用 `mark-submit-failed`。Admin 只可凭同一 `requestId + received_at + worker_id + submission_token`、生产无活动运行、当前待办缺席、精确 final run_id 和脱敏 `actual_write_proof` 调用 `role_cli ops resolve-submitting-external`，迁移为持久 `blocked_external`；不得重试、补写或标记 submitted。该状态在相同 received_at 的后续刷新中保持，只有用户/财务人工明确处理后才可另行决议。
- `runner_item_timeout` 只有在生产 `active_run=false` 且该单据最新台账明确 `write_count=0` 时，才可生成绑定 request_id、checked_at 的 no-write proof，并凭原 submission_token 执行 `role_cli ops mark-submit-failed --confirm-no-write YES --no-write-proof-file ...`。状态机验证失败时按写入状态不明确停止整批。
- 冻结提交路径具备 requestId 级锁、OA 当前待办 `receiveTime`/表单 guard、材料与意见封套校验以及三个后置回执验证。启用生产前必须先刷新队列；`material_contract_version` 旧于 2 的 prepared 项自动回到 queued 并增加下一次 attempt，禁止复用旧材料。

## 失败、修复与人工闭环

下列为单据级失败：`material_collection_failed`、附件缺失/损坏/解码失败、`partial_read`、`remark_template_line_prefix`、业务 `❌/⚠️`、候选已不在待办、流程不受支持，以及明确未写入且外部状态确定的单条失败。记录安全失败码后继续下一条，不输出附件正文或敏感日志。

已证明由确定性运行缺陷造成的误阻断，只能在缺陷修复和聚焦回归通过后，按完全匹配的 `requestId + received_at + failure_code` 执行 `role_cli ops requeue-blocked --confirm-repair YES`。版本或错误码不匹配时保持阻断；普通材料失败仍遵守跨轮索引和冷却规则。

**用户授权的历史技术重审：**用户明确要求重新审核历史技术阻断时，Admin 可以对单条无写入证据的 `blocked_external` 使用 `role_cli ops requeue-blocked-external-manual --confirm-manual-review YES`。命令必须完全匹配 `requestId + received_at + failure_code + contract_sha256`，只允许没有 `write_reconciliation` 来源的历史阻断；它清除旧材料/意见引用、保留一次脱敏释放标记，并创建全新 attempt 重新采集、审核和封套。相同旧阻断索引在这次用户授权的复审期间不得将该项重新覆盖为外部阻断。任何实际写入、写入争议或来源不明项继续保持 `blocked_external`，不得使用此入口。

已进入 `prepared` 的单据若在提交前确定性门禁失败，当天控制台凭该项当前 `received_at`、材料指纹、意见指纹和封套指纹执行一次 `role_cli ops block-prepared`，由状态机精确转为 `blocked`；审核 Agent 已释放原租约，不得用旧 worker lease 调用底层 `block` transition。修复原因并通过回归后，再按上一段的版本与错误码执行 requeue。

当天控制台收到 `OPS_EVENT` 后只核对生产锁、相关进程、任务状态和该项窄队列字段，并按既有状态机做不改变实现的安全闭合；不得现场修改 Skill、代码或 automation。需要修复时把脱敏事件发给 Admin。Admin 建立能够命中当前 failure_code 的可复现检查，完成修复和聚焦测试后返回精确恢复指令；当天控制台再按状态恢复：孤立 `leased` 使用带死亡证明的 `recover-stale`；`prepared` 门禁失败使用精确指纹的 `block-prepared`；已证明修复的 `blocked` 使用完全匹配版本与错误码的 `requeue-blocked`；`submitting` 只按生产台账和 no-write proof 闭合，写入状态不明时停止整批。

**历史技术阻断重对账：**每次成功刷新后，当天控制台必须检查所有仍在实时交集且状态为 `blocked` 的单据。先逐条读取窄队列字段 `request_id、received_at、worker_id、result_code、state`，再判断是否已有配对 `OPS_RESOLUTION`；若该版本未配对，按 `requestId + received_at + failure_code` 去重后补发完整脱敏 `ADMIN_EVENT`，每个 `requestId + received_at + failure_code` 至多补发一次，直至收到配对 resolution、版本变化或单据离开实时交集。禁止用 `blocked_count` 的 aggregate 事件代替单据事件，也不得为了避免重复而省略身份字段。`ops_event_identity_missing` 只表示当前一条阻断在读取后仍无法唯一补全身份；它本身必须携带该条可得的 request_id、received_at、worker_id，且不得覆盖同批其他单据。补发事件只要求 Admin 分析和决定恢复方式，**不得自动 requeue**、不得重跑采集、不得写 OA；因此这些历史阻断必须计入 `open_ops`，批次回执不得声明 `closure=closed`。

发布本契约前已经存在、确实缺少 `event_id` 的旧 `OPEN_OP` 不得伪造事件身份或永久占用 closure。Admin 先逐条核验原始脱敏行对应的故障已经安全闭合，再使用 runtime snapshot 返回的 `unresolved_legacy_open_op_sha256` 追加 `OPS_RESOLUTION|legacy_open_op_sha256=...|action=legacy_event_reconciled`。该兼容键按缺失事件的原始行及其出现序号稳定生成，只用于一次性配对旧格式记录；新 `OPEN_OP` 仍必须携带真实 `event_id`，不得使用兼容键代替。

Admin 每次处理完成后向当天控制台返回一行 `OPS_RESOLUTION|request_id=...|failure_code=...|action=...|queue_state=...|write_state=...|verification=...`；当天控制台在当前或下一 epoch 应用。若安全暂停过 `oa-skill`，须在生产 `active_run=false`、无冲突进程、队列迁移和聚焦验证全部通过后恢复 automation，并立即检查其为 ACTIVE；下一次领取、准备或提交回执必须完成恢复后进度验证，确认 FIFO 真正继续。

**Admin 修复权限：**只有 Admin 可自动修复明确、可逆且不改变财务规则、证据语义、OA 写入边界、队列结构、并发上限或登录方式的小型运行缺陷；修复前保留复现，修复后跑聚焦测试并给出状态机精确恢复指令。财务规则、证据判断、结果模板语义、OA 写入安全、数据库结构、最大并发数、凭据/登录方式和破坏性清理必须人工确认。运行异常不得自动修改财务规则。

**逻辑切换门禁：**自动化或财务反馈只能提出规则候选；用户在当前对话明确纠错，等同于批准该条最小口径，其他推断必须先请示。应用规则前暂停 `oa-skill` 并停止新 claim，等待既有冻结 Writer 自然闭合；受影响的旧规则 `leased/prepared` 结果不得继续提交，准备闭合后以 `policy_change_pending` 精确 `block-prepared`。随后先写脱敏错误案例和已确认反馈，再修改结果契约并增加聚焦测试、完成盲测。验证通过后只对完全匹配的阻断项执行 `requeue-blocked`，以新 attempt 重新取证，确认旧冻结意见不再进入提交路径后恢复 automation 并验证 FIFO 推进。

对准确率有影响的明确财务反馈或用户纠错，必须进入主 Skill 的“错误回归”闭环：先保存脱敏最小错误案例，再更新已确认反馈和聚焦测试，验证后才应用最小规则。技术超时、登录失败或任务卡住本身不能自动改财务判断规则；无法确认正确口径时只记录待样本并向用户请示。

只有下列情况停止整批并暂停生产自动化：并行写入器、生产锁异常、`oa_session_expired`、无法可靠拉取待办、跨 requestId 目录/附件/意见混用，以及 OA 写入状态不明确。若已有冻结 Writer，只等待自然退出并核对，禁止并发重跑。

## Admin 指针与跨日交接

- Admin 由用户在 automation runtime/memory 中指定，保存为脱敏运行指针 `ADMIN|thread_id=...|generation=...|assigned_by=user`；Skill 和项目代码不得硬编码 Admin threadId。角色约束是 Skill 运行规则，不新增 Admin 授权数据库、代码级路径权限或复杂 ACL。
- 当天控制台只在任务系统权威返回当前 Admin 已归档或不存在，且 runtime 中没有更新代际的 Admin 指针时，才可创建一个新的 Admin 并更新指针；超时、权限未知、查询失败或暂时不可见都不得触发替换。新 Admin 从当前仓库、测试、脱敏 `OPS_EVENT/OPS_RESOLUTION` 和交接摘要恢复上下文，不继承附件正文或旧对话全文。
- 每日结束时，当天控制台先停止创建新 epoch；已有审核 Agent 和提交任务自然闭合。写入跨过午夜时必须让原 request 完成回执，下一日控制台不得并行接管同一 request。
- 当天控制台生成一份 `DAILY_HANDOFF|date=...|controller_generation=...|contract_sha256=...|result_contract_sha256=...|queue_generation=...|queue_counts=...|last_receipt_id=...|open_ops=...|admin_generation=...|automation_states=...`。交接只含确定性脱敏状态，不含人员、公司、附件、意见正文或自由叙事历史。
- 下一日控制台读取当前仓库、当天实时队列和 `DAILY_HANDOFF`，返回 `DAILY_HANDOFF_ACK` 后，才归档前一日控制台。不得依赖压缩后的旧控制台对话作为运行事实。

## 线程收尾与批次回执

- 只有桌面可见任务使用线程归档：小时调度任务、当天控制台、独立包装任务和历史可见启动任务创建或迁移成功后，在 automation memory 追加 `THREAD_REGISTER|role=hourly_launcher/controller/packaging/legacy_launcher|thread_id=...|date=...|hour=...|generation=...|request_id=...|received_at=...|attempt=...`；不适用字段写 `-`。归档只认该登记的精确 `thread_id`，不受日期或最近 50 条窗口限制，也不以 `idle` 或 `notLoaded` 作为完成证据。
- 桌面可见任务满足收尾门禁后追加 `ARCHIVE_PENDING|thread_id=...|role=hourly_launcher/controller/packaging/legacy_launcher|receipt_id=...|event_id=...`。小时调度任务只有生成同 receipt_id 的 `HOURLY_DISPATCH_RECEIPT` 后才进入 pending；下一小时任务精确核验并归档。只有这类精确登记才能执行归档补偿。
- 每个普通财务 Reviewer、Writer 和观察子 Agent 是控制台的原生子任务，只有 canonical agent path，不是桌面可归档 threadId。创建成功后记录 `AGENT_REGISTER|role=reviewer/writer/observer|agent_path=...|generation=...|request_id=...|received_at=...|attempt=...`；返回最终 `ITEM_RESULT`、`SUBMIT_RECEIPT` 或 `OPS_EVENT`、对应租约已闭合且该 request 没有活动提交后自然结束，**不得调用 `set_thread_archived`**，也不得把 `/root/...` agent path 写成 `THREAD_REGISTER.thread_id` 或加入 `ARCHIVE_PENDING`。包装准确性协调者是例外的独立可见任务，使用精确 threadId 登记并在回执闭合后进入归档补偿；其内部观察子 Agent 仍不归档。观察子 Agent 的收尾由所属审核 Agent 闭合覆盖回执；不为归档删除 attempt 目录、队列记录或回执。
- **异常持久化先于归档：**任务异常时先追加 `OPEN_OP|event_id=...|request_id=...|received_at=...|failure_code=...|thread_id=...|write_state=...`，再发送实时 `OPS_EVENT`/`ADMIN_EVENT`。只要 `OPEN_OP` 已持久化、单据状态已安全闭合且没有写入不明，任务可以进入 `ARCHIVE_PENDING`；后续 Admin 处理不依赖原任务保持可见。本轮任务自身的异常实时上报规则不变，不得等到下一轮归档才首次报告。
- **精确归档补偿：**每个新小时调度任务先遍历未配对 `ARCHIVE_PENDING` 的精确 thread_id，用 `read_thread` 核对登记任务的最新 turn 已完成、回执 ID 匹配且没有活动写入，再调用 `set_thread_archived(archived=true)`。成功后追加 `ARCHIVE_RECEIPT|thread_id=...|archived=true|receipt_id=...|checked_at=...`；失败或任务仍活动时保留原 pending，记录一次脱敏 `OPEN_OP` 并由下一小时任务幂等重试。归档失败不阻断控制台发现、审核 Agent 派发或其他 requestId 的提交；只有实际写入不明或异常尚未持久化时才保留任务并暂停相关 request。
- 当前小时调度任务在自身结束前不得归档自己；下一小时任务只归档已经生成匹配 `HOURLY_DISPATCH_RECEIPT` 的前一小时任务。当天控制台在当日运行中不例行归档；前一日控制台只有在下一日控制台返回 `DAILY_HANDOFF_ACK` 后，才追加其 `ARCHIVE_PENDING` 并按精确归档补偿处理。
- 审核 Agent 只向当天控制台返回 `ITEM_RESULT` 或 `OPS_EVENT`；当天控制台生成 `EPOCH_RECEIPT` 与未解决 `OPS_DIGEST`，并只向 Admin 转发需要修复或人工决策的 `ADMIN_EVENT`。Admin 用 `OPS_RESOLUTION` 或 `SKILL_RELEASE` 回传，不接收附件正文。
- 每次小时刷新记录：清单 generation、候选数、准备积压、目标/活动任务数和监控实际状态。批次在首次审核/写入和每段控制面暂停的开始、结束分别记录脱敏时间戳；`control_pause_seconds` 只累计代际切换、状态机恢复或调度故障造成的“无审核、无写入且 FIFO 未结束”时段，附件下载、审核和唯一写入器等待不得计作暂停。批次结束使用 `EPOCH_RECEIPT|generation=...|loaded_generation=...|latest_generation=...|generation_transition=...|found=...|attempts_started=...|submitted=...|blocked_new=...|blocked_carried_forward=...|requeued_after_repair=...|remaining=...|open_ops=...|epoch_elapsed_seconds=...|items_timed=...|avg_attempt_seconds=...|p95_attempt_seconds=...|flow_timing=...|productive_submit_window_seconds=...|control_pause_seconds=...|reviewer_slots_peak=...|reviewer_slots_available=...|observer_slots_peak=...|capacity_probe_attempts=...|capacity_rejections=...|closure=...|stop_reason=...`；其中 `remaining` 表示剩余候选；不包含附件正文、人员、公司或凭据。`attempts_started` 只计本 epoch 实际创建的新 attempt；`blocked_new` 只计本 epoch 从非 blocked 转为 blocked 的单据；`blocked_carried_forward` 只计刷新时已经 blocked 且本 epoch 未重新领取的单据；`requeued_after_repair` 只计本 epoch 通过完全匹配修复条件重新入队的单据，四项不得用历史 `blocked` 总数替代。`productive_submit_window_seconds` 是首条至末条提交回执间隔；`reviewer_slots_peak` 是本 epoch 同时活动审核数，`reviewer_slots_available` 是实际可分配审核槽位上限，二者不得以配置上限代替。`flow_timing` 按五个 `workflow_key` 分别输出本轮完成数、平均值和 P95，零样本明确写 0；`capacity_probe_attempts` 与 `capacity_rejections` 只计真实任务创建调用及其平台拒绝，不得把队列期望槽位当成实际并发。
- 每轮时效从 epoch 建立至最终回执闭合，所有阶段秒数使用单调时钟计算并取非负整数；审计时间点另用 UTC 时间戳。`items_timed` 必须等于本轮已经成功或阻断闭合且发出最终 `ITEM_TIMING` 的 attempt 数；样本不足 20 条时 P95 取排序后的最近上界样本，不得伪造精度。后期性能复盘先比较 `collection_seconds、observation_seconds、judgment_seconds、prepared_wait_seconds、writer_total_seconds`，再决定优化采集、视觉、调度或写入，禁止只凭“平均每单耗时”盲目增加审核 Agent。
- 当 `open_ops>0` 时，`EPOCH_RECEIPT` 必须使用 `closure=awaiting_ops_resolution`，不得声明 `closure=closed`；这时允许结束调度 Goal，但当天控制台必须保留未解决事件并等待 Admin 的精确 `OPS_RESOLUTION`。只有所有 `OPS_EVENT` 都已配对 `OPS_RESOLUTION`、每个需要恢复的队列状态已迁移，且恢复后进度验证完成时，才使用 `closure=closed`。automation 状态与审核池不一致同样不得声明 closed。
